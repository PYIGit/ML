# 개발 로드맵: 제조 AI/ML 의사결정 지원 시스템

- 작성일: 2026-10-22
- 상태: 초안 (단계 1 진행 중)
- 이 문서는 프로젝트의 단계별 계획을 정리한 것이며, 각 단계의 실제 발견 사항에 따라 수정한다. 수정 시에는 변경 이유를 아래 "변경 이력"에 기록한다.

---

## 1. 프로젝트 목표

공개 제조 데이터셋(Kaggle Bosch Production Line Performance)을 기반으로 ML 예측 모델과 의사결정 지원 기능을 개발하고, 실제 제조 운영을 모사하는 시뮬레이터와 연결한 통합 시스템을 구축한다.

최종 시스템의 흐름:

1. 제조 데이터 수집 및 분석
2. 데이터에 근거한 ML 예측
3. 예측 결과를 바탕으로 위험도와 판단 근거 제공
4. 가능한 경우 후속 조치 또는 추가 검사 권고
5. Backend API와 DB를 통한 상태 및 이력 관리
6. Frontend 대시보드를 통한 모니터링
7. LLM/Agent가 실제 시스템 데이터와 ML 결과를 조회하여 설명하고 의사결정을 지원

이 프로젝트는 개인 포트폴리오 프로젝트다. 실제 기업의 운영 데이터나 내부 시스템은 사용하지 않는다.

## 2. 설계 원칙 (모든 단계에 적용)

| 원칙 | 내용 |
|---|---|
| 데이터가 먼저 | 문제 정의와 모델 설계는 EDA 결과를 근거로 확정한다. |
| 사실과 가정의 구분 | 데이터에서 관찰한 사실, 모델이 학습한 패턴, 프로젝트가 설정한 가상 운영 규칙을 명확히 구분한다. 상관관계를 인과관계로 단정하지 않는다. |
| 예측과 의사결정의 구분 | 예측 성능이 좋다는 사실이 특정 조치의 효과를 보장하지 않는다. 검증되지 않은 조치는 추가 검사, 작업자 확인 등 보수적 권고로 시작한다. |
| LLM은 실제 데이터에 근거 | LLM은 Backend API로 조회한 데이터에 근거해 설명한다. 초기에는 읽기 전용이며, 설비 제어나 운영 명령 실행은 범위에서 제외한다. |
| 단순한 것부터 | 필요 이상의 프레임워크나 서비스를 도입하지 않는다. baseline을 먼저 만들고 검증 결과에 따라 복잡도를 높인다. |
| 재현성과 기록 | 전처리와 학습은 재현 가능하게 만들고, 데이터 출처, 버전, 전처리 규칙, 실험 설정을 기록한다. |
| 작은 단위의 변경과 검증 | 변경은 작게 나누어 진행하고, 실행한 테스트와 미검증 사항을 구분해서 보고한다. |
| 위험한 작업 금지 | 데이터 삭제, Git 이력 변경, 강제 푸시는 임의로 하지 않는다. Git commit과 push는 반드시 확인을 받은 뒤 수행한다. |

## 3. 단계별 로드맵

각 단계는 "목표 / 주요 작업 / 산출물 / 완료 기준 / 미확정 사항"으로 정리한다. 단계 번호는 인수인계 시 합의한 12단계 순서를 따르며, `DOCS/` 아래 단계별 디렉터리 번호(`01_SETUP` 등)와 일치시킨다.

### 단계 1. 개발 환경과 프로젝트 기반 구축 (진행 중)

- 목표: 이후 작업을 안정적으로 수행할 수 있는 저장소 구조와 도구 설정을 갖춘다.
- 주요 작업
  - `.gitignore` 작성 (`.venv/`, `data/`, 캐시, 노트북 체크포인트, 환경 변수 파일 등)
  - 기본 디렉터리 구조 결정 (예: `data/`, `notebooks/`, `src/`, `tests/`, `DOCS/`)
  - `pyproject.toml`, `.python-version`, `uv.lock` 커밋 여부 결정
  - 최소한의 개발 도구 선정 (린터, 포매터, 테스트 러너). 도입 시 이유를 기록한다.
  - README 보강
- 산출물: `.gitignore`, 디렉터리 골격, 갱신된 README, 이 로드맵 문서
- 완료 기준: 데이터 파일이 실수로 커밋될 수 없는 상태이고, 새 환경에서 `uv sync`만으로 재현 가능하다.
- 현재 상태 (2026-10-22 확인)
  - Git 저장소와 원격 `origin` 연결 완료, `main` 브랜치가 `origin/main`과 동기화됨
  - 추적 중인 파일은 `README` 하나. `.python-version`, `pyproject.toml`, `uv.lock`, `.gitignore`, `DOCS/`, `src/`는 미추적 상태
  - `.gitignore` 작성 완료 (`DATA/` 전체 무시, `DATA/raw/bosch/`는 이중 장치로 별도 무시)
  - 디렉터리 구조 확정 및 생성 완료. 상세는 `DOCS/01_SETUP/DIRECTORY_STRUCTURE.md` 참고
  - `.venv/`에 Python 3.12.3 설치됨
- 미확정 사항: 개발 도구 선택(린터, 포매터, 테스트 러너), `src/ml` 패키지를 import 가능하게 만드는 방식

### 단계 2. 공개 데이터셋 확보

- 목표: Bosch 데이터셋을 이용 조건에 맞게 내려받고 로컬에 안전하게 보관한다.
- 주요 작업
  - Kaggle 대회 규칙 확인 및 동의, 데이터 이용 조건과 재배포 가능 여부 기록
  - 파일별 크기 확인 (다운로드 전)
  - 저장 위치 결정. WSL 디스크(여유 약 949 GB)를 우선 검토하되 Windows 측 접근 필요성도 고려한다.
  - 다운로드 방법 결정 (Kaggle API 또는 수동 다운로드)
  - 다운로드한 파일의 체크섬 또는 크기 기록
- 산출물: `data/raw/` 아래 원본 파일 (Git 미추적), 데이터 출처와 버전을 기록한 문서 (`DOCS/DATA.md` 등)
- 완료 기준: 모든 필요 파일이 로컬에 있고, 출처와 조건이 문서화되어 있으며, Git에 올라가지 않는다.
- 미확정 사항: 실제 파일 크기, Kaggle API 토큰 사용 여부, 압축 해제 후 용량

### 단계 3. 데이터 구조 탐색 및 EDA

- 목표: 데이터에 실제로 어떤 정보가 있는지 파악하고, 문제 정의에 필요한 근거를 확보한다.
- 주요 작업
  - 파일 구조 파악: `train_numeric`, `train_categorical`, `train_date` 및 테스트 파일의 행/열 수, 컬럼 명명 규칙(라인, 스테이션, 피처 ID)
  - 메모리 제약(약 7.6 GiB)을 고려한 읽기 전략: 샘플링, 청크 처리, 필요한 컬럼만 읽기, 효율적인 포맷(예: Parquet)으로 변환
  - 결측 패턴 분석: 어떤 부품이 어떤 스테이션을 거치는지 결측 구조로 추정
  - 타깃(`Response`) 분포와 클래스 불균형 정도 확인
  - 날짜 피처의 의미와 범위, 시간 순서 분석
  - 범주형 피처의 카디널리티와 유용성
  - 예측 시점에 이용 가능한 데이터가 무엇인지 검토 (누수 위험 식별)
- 산출물: EDA 노트북 또는 스크립트, 발견 사항 요약 문서 (`DOCS/EDA_FINDINGS.md` 등)
- 완료 기준: "데이터에서 확인된 사실"과 "추정"을 구분한 발견 사항 목록이 있고, 다음 단계의 문제 정의에 필요한 질문에 답할 수 있다.
- 미확정 사항: 데이터 로딩 도구 선택(pandas, polars 등). 메모리 제약을 고려해 EDA 초기에 결정한다.

### 단계 4. 문제 정의 및 가상 제조 현장 설계

- 목표: EDA 결과를 근거로 풀어야 할 문제와, 시스템이 동작할 가상 제조 현장의 운영 규칙을 정의한다.
- 주요 작업
  - 예측 과제 정의: 무엇을, 언제, 어떤 입력으로 예측하는가
  - 평가 지표 선정과 근거: 이 시스템의 평가 요소(운영 의사결정 관점)에 맞춰 구성한다. 대회 지표(MCC)는 기준으로 삼지 않으며, 대회가 풀려던 문제가 무엇이었는지만 문제 정의의 참고 자료로 활용한다. 클래스 불균형을 고려한다.
  - 데이터 분할 전략 (시간 기반 분할 여부는 날짜 피처 분석 결과에 따라 결정)
  - 가상 제조 현장 정의: 라인, 스테이션, 부품 흐름, 검사 지점. 데이터에서 확인된 구조에 근거하되, 추가한 가정은 명시한다.
  - 의사결정 시나리오 초안: 예측 결과가 어떤 운영 판단으로 연결되는가
- 산출물: 문제 정의 문서, 가상 현장 설계 문서, 설계 결정 기록
- 완료 기준: 예측 대상, 입력, 평가 지표, 분할 전략이 문서로 확정되었고, 가상 현장의 가정이 사실과 구분되어 기록되어 있다.
- 미확정 사항: 전부. 이 단계의 내용은 EDA 이후에만 결정한다.

### 단계 5. 데이터 파이프라인과 전처리

- 목표: 원본 데이터에서 학습 가능한 형태까지의 변환을 재현 가능하게 만든다.
- 주요 작업
  - 원본 → 중간 포맷 → 피처 테이블로 이어지는 변환 단계 정의
  - 결측 처리, 피처 선택, 범주형 인코딩 규칙 확정
  - 누수 방지 검증 (분할 이후에만 통계를 계산하는지 등)
  - 전처리 코드의 테스트 작성
- 산출물: `src/` 아래 전처리 모듈, 전처리 규칙 문서, 테스트
- 완료 기준: 동일한 입력에서 동일한 출력이 나오고, 전처리 규칙이 문서와 코드에서 일치한다.

### 단계 6. ML baseline 구축, 모델링 및 평가

- 목표: 단순한 baseline을 먼저 만들고, 검증 결과에 따라 모델을 개선한다.
- 주요 작업
  - baseline (예: 단순 규칙 또는 로지스틱 회귀, 트리 기반 모델) 구축과 평가
  - 실험 설정 기록 (데이터 버전, 피처, 하이퍼파라미터, 분할, 지표)
  - 불균형 처리 방법 비교 (가중치, 샘플링, 임계값 조정)
  - 모델 설명 가능성 검토: 위험도 근거 제공에 어떤 정보를 쓸 수 있는가
  - 모델 직렬화와 로딩 방식 결정
- 산출물: 학습/평가 스크립트, 실험 결과 기록, 저장된 모델 아티팩트 (Git 미추적)
- 완료 기준: baseline 대비 개선 여부가 동일한 평가 조건에서 비교되어 있고, 선택한 모델의 한계가 문서화되어 있다.
- 미확정 사항: 실험 추적 도구 도입 여부. 초기에는 파일 기반 기록으로 시작하고 필요가 생기면 검토한다.

### 단계 7. 데이터 시뮬레이터 개발

- 목표: 실제 데이터가 지속적으로 들어오는 것과 유사한 운영 흐름을 만들어 시스템 통합을 검증한다.
- 주요 작업
  - 생성 규칙 정의: 공개 데이터의 분포를 참고하되, 근거 없는 물리적 관계나 인과관계는 만들지 않는다.
  - 정상 흐름 외에 누락 데이터, 이상치, 지연, 예외 상황 생성
  - 재현 가능한 시드 기반 생성
  - 시뮬레이션 데이터와 실제 데이터의 구분 표시
- 산출물: 시뮬레이터 모듈, 생성 규칙 문서, 테스트
- 완료 기준: 시뮬레이터가 단계 4에서 정의한 가상 현장 규칙과 일치하고, 예외 상황을 의도적으로 발생시킬 수 있다.
- 미확정 사항: 세부 생성 규칙. 데이터와 모델 특성을 이해한 뒤 구체화한다.

### 단계 8. 의사결정 엔진 개발

- 목표: 예측 결과를 위험도와 판단 근거, 권고사항으로 변환한다.
- 주요 작업
  - 위험도 등급 정의와 임계값 근거
  - 판단 근거 생성 (모델 설명 정보, 관련 피처, 이력)
  - 권고 규칙 정의: 효과가 검증되지 않은 조치는 추가 검사, 작업자 확인 등 보수적 권고로 시작
  - 조치의 효과와 비용에 관한 가정 명시
  - 규칙의 테스트
- 산출물: 의사결정 모듈, 규칙과 가정 문서, 테스트
- 완료 기준: 동일한 예측 입력에 대해 동일한 위험도와 권고가 나오고, 각 권고의 근거와 가정이 추적 가능하다.

### 단계 9. Backend와 DB/API 개발

- 목표: 데이터 수신, 예측 실행, 결과 저장, 이력 조회를 API로 제공한다.
- 주요 작업
  - 데이터 모델 설계 (부품, 측정값, 예측 결과, 위험도, 권고, 이력)
  - API 설계 (수신, 예측, 조회). LLM/Agent가 사용할 읽기 전용 조회 API 포함
  - DB 선택과 근거 (초기에는 단순한 선택을 우선)
  - 시뮬레이터와의 연결
  - API 테스트
- 산출물: Backend 서비스, API 문서, 스키마, 테스트
- 완료 기준: 시뮬레이터 → Backend → DB → 조회 흐름이 동작하고, 예외 상황이 적절히 처리된다.
- 미확정 사항: 프레임워크와 DB 선택. 필요 시점에 대안과 근거를 정리한 뒤 결정한다.

### 단계 10. Frontend 및 운영 대시보드 개발

- 목표: 현재 상태, 위험도, 권고, 이력을 모니터링할 수 있는 화면을 제공한다.
- 주요 작업
  - 화면 요구사항 정의 (어떤 사용자가 어떤 판단을 위해 무엇을 보는가)
  - Backend API 연동
  - 시뮬레이션 데이터임을 화면에 명시
- 산출물: 대시보드, 화면 요구사항 문서
- 완료 기준: 시뮬레이터가 동작하는 동안 대시보드가 갱신되고, 이력을 조회할 수 있다.
- 미확정 사항: Frontend 기술 선택

### 단계 11. LLM/Agent 통합

- 목표: LLM이 Backend API를 통해 실제 시스템 데이터와 ML 결과를 조회하고, 그 데이터에 근거해 설명하도록 한다.
- 주요 작업
  - 읽기 전용 도구 정의 (상태 조회, 예측 결과 조회, 권고 조회, 이력 조회)
  - 근거 없는 답변을 방지하는 설계 (조회 결과 외의 상태를 만들어내지 않도록)
  - 응답에 근거 데이터 출처 표시
  - 평가: 조회 결과와 설명의 일치 여부 검증
- 산출물: Agent 모듈, 도구 정의, 평가 기록
- 완료 기준: LLM의 설명이 API 조회 결과와 일치하며, 데이터가 없는 질문에는 없다고 답한다.
- 범위 제외: 자율적인 설비 제어, 실제 운영 명령 실행

### 단계 12. 통합 테스트, 배포, 문서화

- 목표: 전체 시스템을 하나의 흐름으로 검증하고, 재현 가능한 형태로 정리한다.
- 주요 작업
  - 시뮬레이터 → Backend → 의사결정 → 대시보드 → LLM까지 통합 시나리오 테스트
  - Docker 기반 실행 환경 정리
  - 설계 결정 기록 정리, README 완성, 한계와 향후 과제 기록
- 산출물: 통합 테스트, 실행 가이드, 최종 문서
- 완료 기준: 새 환경에서 문서만 보고 전체 시스템을 실행할 수 있다.
