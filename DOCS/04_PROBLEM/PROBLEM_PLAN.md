- 작성일: 2026-11-13
- 상태: 승인 (2026-11-13). 4-1, 4-2 완료 (2026-11-13)
- 관련 문서: `DOCS/ROADMAP.md` 단계 4, `DOCS/03_EDA/EDA_FINDINGS.md` 1절(단계 4 입력 요약), 2절(아직 모르는 것)

## 1. 목표

단계 4는 분석하는 단계가 아니라 정하는 단계다. 단계 3(EDA)에서 알아낸 것을 근거로 아래 다섯 가지를 정해서 문서로 확정한다. 단계 5(전처리)부터는 여기서 정한 것을 그대로 따른다.

| # | 정할 것 | 정해지면 무엇에 쓰이는가 |
|---|---|---|
| 1 | 가상 현장: 이 프로젝트의 공장이 어떻게 생겼고 부품이 어떻게 흐르는가. 데이터로 확인하지 못한 것 중 무엇을 가정으로 둘 것인가 | 단계 7(시뮬레이터)이 이 흐름대로 부품을 흘린다. 단계 4의 나머지 결정이 이 현장을 전제로 한다 |
| 2 | 의사결정 시나리오: 불량 예측이 나오면 누가, 언제, 무엇을 하는가 | 예측 시점(3번)과 평가 지표(4번)가 이것으로 정해진다. 단계 8(의사결정 엔진)의 출발점이다 |
| 3 | 예측 과제: 무엇을, 언제, 어떤 입력으로 예측하는가 | 단계 5가 만들 입력 표, 단계 6이 학습할 모델 |
| 4 | 평가 지표: 모델이 쓸 만한지를 무엇으로 재는가 | 단계 6의 모델 비교 기준 |
| 5 | 데이터 분할: 학습용과 검증용을 어떻게 나누는가 | 단계 5, 6의 모든 실험 |

이 단계에서 하지 않는 것:

- 모델 학습과 성능 측정(단계 6). 지표는 정의만 하고 값은 재지 않는다.
- 전처리 코드 작성(단계 5).
- 시뮬레이터의 세부 생성 규칙(단계 7). 여기서는 흐름과 가정까지만 정한다.

## 2. 하위 단계

정하는 순서가 중요하다. 예측 시점과 지표는 "예측으로 무엇을 할 것인가"가 먼저 정해져야 고를 수 있다. 그래서 현장 → 시나리오 → 예측 과제 → 지표 → 분할 순서로 간다.

| 단계 | 정할 것 | 근거로 쓸 EDA 결과 | 직접 정하셔야 하는 것 | 데이터 계산 |
|---|---|---|---|---|
| 4-1 가상 현장 | 라인 4개, 스테이션 52개의 흐름과 갈림길. 검사 지점. 가정 목록 | `EDA_FINDINGS.md` 1-6(흐름, 시간), 2절의 "데이터로는 알 수 없는 것" 5개 | 5개를 각각 가정으로 둘지: `Response`가 정해지는 시각, 짝이 생기는 이유, `L3_S33`을 건너뛰는 이유, 불량이 몰린 시기의 원인, date 값의 단위 | 없음 |
| 4-2 의사결정 시나리오 | 예측 결과가 이어지는 운영 판단(예: 추가 검사, 작업자 확인). 시점마다 할 수 있는 조치 | `EDA_FINDINGS.md` 1-2(세 시점의 측정값 수와 남은 시간) | 이 시스템이 돕는 판단이 무엇인지. 예측 시점 세 가지 중 어느 것을 쓸지(여러 개도 가능) | 없음 |
| 4-3 예측 과제 | 예측 대상, 예측 시점, 입력 범위 | `EDA_FINDINGS.md` 1-1, 1-2, 1-3 | 짝(측정값이 똑같은 이웃 부품)을 입력으로 쓸지. 부품의 시각을 입력으로 쓸지 | 4-2에서 "L2 또는 L3에 들어가기 전"을 고르면, 그 시점까지의 값만으로 찾은 짝의 수를 계산한다 |
| 4-4 평가 지표 | 주 지표 1개와 보조 지표. 비교 기준(모델 없이 얻는 성능) | `EDA_FINDINGS.md` 1-5(불량 0.58%, 측정값이 같은데 정답이 다른 부품) | 4-2의 시나리오에서 무엇이 더 큰 손해인지: 불량을 놓치는 것인가, 정상 부품을 불량으로 의심하는 것인가 | 없음 |
| 4-5 데이터 분할 | 학습용과 검증용을 나누는 기준과 비율 | `EDA_FINDINGS.md` 1-4(시기별 불량률, 짝은 같은 시각) | 시간 기준으로 나눌지, 무작위로 나눌지 | 후보마다 학습용과 검증용의 부품 수와 불량 수를 센다. 짝이 양쪽에 갈라지는지 확인한다 |
| 4-6 확정 | 4-1 ~ 4-5의 결정을 한 문서로 모은다. 단계 4 완료 기준을 확인한다 | 4-1 ~ 4-5의 결과 | 없음 | 없음 |

- 4-1, 4-2, 4-4, 4-6은 문서 작업이다. 4-3과 4-5만 데이터를 다시 읽는다.
- 하위 단계의 순서와 구성은 진행하면서 바뀔 수 있다. 바꿀 때는 이유를 말하고 확인받는다.

## 4. 진행 방식

단계 3에서 정한 방식을 그대로 따른다.

- 하위 단계마다 설계 문서를 먼저 쓰고, 컨펌을 받은 뒤 구현한다.
- 결과는 결론을 먼저, 근거를 그다음에 적는다. 정하는 데 쓰이지 않는 내용은 적지 않는다.
- 데이터로 확인한 사실과 이 프로젝트가 둔 가정을 구분해서 적는다. 가정에는 "가정"이라고 적는다.
- 문서를 고칠 때는 고칠 내용을 먼저 보여 주고 컨펌을 받은 뒤 고친다.
- test 파일은 쓰지 않는다. train과 같은 부품들이고 정답이 없다(`EDA_FINDINGS.md` Q9).
- 대회 지표(MCC)는 기준으로 삼지 않는다(로드맵 단계 4).

## 5. 완료 기준

로드맵 단계 4의 완료 기준을 풀어 쓴 것이다.

1. `PROBLEM_DEFINITION.md`에 예측 대상, 예측 시점, 입력 범위, 평가 지표, 분할 방법이 정해져 있다.
2. 가상 현장의 내용마다 데이터로 확인한 사실인지, 이 프로젝트의 가정인지가 표시되어 있다.
3. 예측 결과가 어떤 운영 판단으로 이어지는지가 적혀 있다.
4. 결정마다 무엇을 두고 골랐고 왜 그것을 골랐는지가 하위 단계 문서에 남아 있다.
5. 분할 표가 저장되어 있고, 스크립트로 다시 만들 수 있다.
